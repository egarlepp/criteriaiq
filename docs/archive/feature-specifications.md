- **Data-Directory Read-Only Watcher (Task #769):** `server/services/data-dir-watcher.ts` polls `checkDataDirWritable()` every 5 minutes (first run after 30 s, env: `DATA_DIR_WATCHER_INTERVAL_MS`, `DATA_DIR_WATCHER_FIRST_RUN_DELAY_MS`). On every state TRANSITION (writable ↔ not-writable) it emails every approved Admin via the existing SMTP plumbing (reuses `migration-failure-emailer._internals` for SMTP + admin lookup) and updates an in-process snapshot. Per-state dedupe (default 1 h, env `DATA_DIR_WATCHER_DEDUPE_MS`) prevents flap-spam — at most one read-only email and one recovery email per dedupe window. The watcher also fires a one-shot read-only email when a fresh boot's first probe finds the directory already unwritable, so a misconfigured volume mount is reported within minutes rather than waiting for a transition that may never come. Snapshot is exposed via the admin-only `GET /api/system/data-dir-status` endpoint and rendered as a top-of-page red `DataDirReadOnlyBanner` (admin-gated, dismissible per-snapshot, auto-resurfaces on a different failure mode or when the next failure follows a recovery).

- **Email Automation Audit Pipeline & send_email Rebuild (v0.7.60):** Five connected schema-mismatch bugs that had left every workflow-automation rule firing into the void are fixed end-to-end. The `email_rule_audits` table's modern schema (`event_key` / `input` / `decision` / `reason` / `email_log_id` / `execution_time_ms` / `metadata`) had not been reflected in the engine or its consumers — every insert in `server/email/email-automation-engine.ts:recordAudit` and `server/routes/email-automation-routes.ts` consumer queries threw on non-existent columns (`projectId`, `triggerKey`, `triggeredAt`, `conditionsSnapshot`, `actionsSnapshot`) and was silently swallowed by the call-site `void evaluateAndExecute(...).catch(...)`. The fix renames `recordTrigger` → `recordAudit`, writes the real schema fields, removes the `if (projectId)` gate so user-lifecycle triggers (`user.registration_completed`, `user.first_login`) audit too, and rewrites the dedup check to use `event_key` + `input->>'projectId'` for the project-less case. Two consumer endpoints (`/api/email-automation/stats`, `/api/email-automation/execution-feed`) were similarly reading `audit.actionsSnapshot.executionResults` and `row.project_id` / `row.conditions_snapshot` — all undefined on the real schema — so the KPI cards always returned `0` / `--%` and the feed's ruleName-sort branch 500-ed on the SELECT itself; all three formatter blocks (raw-SQL ruleName sort, in-memory duration sort, default created_at sort) now read `metadata.executionResults`, `input.projectId`, and the top-level `executionTimeMs` field. The `send_email` action had its own two-layer bug that prevented any rule-based welcome email from sending: the template lookup queried `eq((emailTemplates as any).key, templateKey)` against a non-existent field, producing malformed SQL `WHERE = $1`; with that fixed the placeholder pass next threw on `(template as any).htmlBody.replace` because the schema fields are `emailContent` / `htmlContent` / `textContent`. Both fixed plus the placeholder pass defaults to `""` so body-less templates don't crash. Adjacent bugs caught while in the area: `executeSuppressFor` was double-writing an audit with the legacy columns (always threw, so suppressions never persisted) — now the parent `executeActions` audit carries the suppression in `metadata.executionResults` and `checkActiveSuppression` reads it back via a JSONB containment query; `logSalesforceAudit` had the same legacy-column insert and was rewritten to the modern shape. Verified live: a POST `/api/register` now produces an audit row with `decision='matched'`, `execution_time_ms=12`, and `metadata.executionResults[0].status='executed'`; the stats endpoint returns `{ activeRulesCount: 1, emailsSent24h: 1, successRate: 100 }` and the execution feed lists the rule run with action breakdown.
- **Email Template Dialog Hydration & Default Design Wrapping (v0.7.60):** Two connected bugs in the Edit Email Template dialog at `client/src/components/communications/email-templates/EmailTemplatesSection.tsx`. (1) The dialog's React `key` prop mixed `Date.now()` into its value, forcing unmount/remount on every parent re-render and resetting in-flight `formData` state — fixed by switching to `key={\`edit-\${selectedTemplate.id}\`}`. (2) After (1), the form's post-mount `useEffect` hydration was racing with Radix Select's `onValueChange` callbacks that fire on certain controlled-value transitions: the Category and Email Type Selects had handlers shaped `(value) => setFormData({ ...formData, X: value })` that closed over the stale pre-hydration `formData` (with `designId: null`), so when Radix fired its spurious `onValueChange` during the hydration transition the spread reverted `designId` from `1` back to `null` on top of just resetting the field the Select cared about. Two-layer fix: a lazy `useState(() => initialData ? {...} : {...})` initializer builds the formData synchronously on the first render so the Selects never see a controlled-value transition, plus every `setFormData({ ...formData, X })` callsite was converted to `setFormData(prev => ({ ...prev, X }))` so any future closure-bound handler can't reset state. Also rebrand-resilient at the design-lookup layer: both server-side wrapper (`server/email/email.ts`) and the template form's create-mode default-selection use `is_default = true` instead of literal name "CriteriaIQ Default"; a new `storage.getDefaultEmailDesign()` helper centralises the query. The `getEmailDesignByName` SELECT was missing `design_variables` from its column list, silently coercing `defaultDesign.designVariables` to `undefined` then `{}` in the wrapper — so every branding placeholder (`{{logoSrc}}`, `{{HEADER_BG}}`, etc.) rendered as a literal string in the final email; fixed by adding the missing columns to the SELECT.
- **Access Code assignedRole at Registration (v0.7.60):** The `/api/register` endpoint's anti-privilege-escalation guard (which drops `req.body.role` to prevent a self-elevation POST) was also discarding the trusted `assigned_role` value off the validated access code row, so every signup-with-code landed on `DEFAULT_REGISTRATION_ROLE = "Engineer"` regardless of what role the admin chose when creating the code in Configuration → Login Management. The fix in `server/auth/simpleAuth.ts` looks up the access code by `accessCodeId` server-side after password validation and, if the code carries an `assignedRole`, honours it — wrapped in a roles-table whitelist check via a new `storage.getRoleByName(name)` method so a stale or hand-edited code targeting a deleted role falls back to `DEFAULT_REGISTRATION_ROLE` rather than creating an orphan-roled account. The trust boundary stays intact: `role` from `req.body` is still ignored.

The component encapsulates the Tailwind 4 `bg-[var(--var)]` syntax that the v3 `bg-[--var]` shorthand silently dropped, preventing the class of regression that landed a default-variant pill in the Account Portal table. CLAUDE.md mandates this component as the only allowed render path for status pills. The Account Portal **project card** (`client/src/components/shared/ProjectCard.tsx`) was redesigned: solution icons render with a ` | ` separator between solution names, tag pills appear below the solution name (wired through `LiveProjectCard`), the status + end-date row moved to the top of the card, and the progress ring is `absolute top-4 right-4` with `pr-16` reserving its lane so the ring stays in place without inflating row height.
